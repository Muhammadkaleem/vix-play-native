# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VixPlay is a native Android media player — a modern alternative to MX Player. Kotlin + Jetpack Compose, Media3/ExoPlayer + an FFmpeg audio-decoder extension, indigo→violet brand. A shipping Play Store app (`com.devbytes.vixplayer.app`): video + audio libraries, full player, network streaming (URL, SMB, FTP), Home dashboard, AdMob monetisation with a rewarded "Pro" tier, Firebase.

Product docs are in `vix-play-docs/media-player-docs/`; design assets (colour tokens, typography, icons, launcher icon) in `config-vix-play/player-design-assets/`. Both describe the original plan — where they disagree with the code, the code wins (see below).

## Standing development guidelines (mandatory)

These apply to **every** feature, bug fix, UI improvement and refactor.

**The current codebase is the source of truth.** It outranks this file's older sections, the product docs, earlier prompts and pasted templates. Before designing anything, inspect what the code actually does today (theme, typography, navigation, architecture, components); never act on a documented configuration without checking it still holds. When you find this file out of date, correct it in the same change.

**UI / UX**
- Respect the currently configured default theme (`ThemeMode.LIGHT`, see Theming) and make every change work in **both Light and Dark** (and AMOLED / Material You, which derive from them).
- Reuse the typography in `ui/theme/Type.kt` (Inter; JetBrains Mono for timecodes) and the existing components, spacing, colour tokens and motion. No hardcoded colours.
- No global design changes (theme, fonts, navigation, shared components) as a side effect of a single feature.

**Working independently**
- Given a feature name, description, screenshot, video or mockup: analyse it, explore the relevant code, and fill in missing details with reasonable decisions. Ask only when a genuinely critical requirement can't be determined from the code or the references.
- Think the whole feature through before coding — flows, edge cases, lifecycle, performance, accessibility — then implement it; don't stop at a plan.
- Follow the existing architecture, reuse what exists, avoid unnecessary refactoring of unrelated code.

**Validation (before calling anything done)**
- Verify in both Light and Dark.
- Exercise the relevant user flows and edge cases, on a device/emulator where the change is visual or behavioural.
- Run the unit tests and a build (`./gradlew test`, `./gradlew assembleDebug`); check for regressions in neighbouring features.
- Report anything unverified or unresolved honestly.

**Keep this file in sync.** When a project decision changes, update the relevant section here and add an entry to the progress log below.

## Architectural decisions

| Concern | Decision |
|---|---|
| **Module structure** | Single module (`:app`). The tech-architecture doc's multi-module layout is reference only. |
| **DI** | Hilt. `PlayerController` is an app-wide **`@Singleton`** owning the one `ExoPlayer`; `PlaybackService` (`MediaSessionService`) hosts the session for background audio, notification and lock-screen controls. UI calls the player directly (single process, no `MediaController`). |
| **Navigation** | Navigation Compose with **string route constants** in `navigation/Routes.kt`, one nested graph per bottom-nav tab (Home · Video · Audio · Network · Settings) wired in `ui/VixPlayNavGraph.kt`. Tab switches go through `switchTab` (`popUpTo(HOME_ROUTE)` + save/restore state). External `ACTION_VIEW`/`SEND` intents are parsed in `MainActivity`. |
| **Application ID** | `com.devbytes.vixplayer.app` — permanent (Play Store listing exists). |
| **Storage** | MediaStore + granular media permissions as primary; SAF tree access for folder browsing; `MANAGE_EXTERNAL_STORAGE` as opt-in power mode only (with Play Console declaration). |
| **FFmpeg** | Media3 FFmpeg extension built via Google's provided script, checked in as a local `.aar` (`app/libs/`, built by `scripts/build-ffmpeg-aar.sh`). **Audio decoders only** — that is all the Media3 extension provides; there is no software video fallback. Must be rebuilt whenever the media3 version changes. No custom FFmpeg build. |
| **AC3/DTS** | Omitted. HW decode covers most devices. Show the codec name in the unsupported-format error; revisit licensing at 1.0. |
| **Subtitles** | Media3 built-in renderer (SRT + basic SSA) plus user styling via `SubtitleView`. libass (full styled ASS/SSA fidelity) is a fast-follow — not a blocker. |
| **Pro entitlement** | No Play Billing. "Pro" is a **rewarded-ad time bank** (`ProRepository`, up to 48 h) that removes ads only — every feature stays free. A paid tier would need Billing + backend verification. |
| **Analytics** | Firebase Crashlytics + Analytics (Analytics enabled 2026-10-07 at the user's request; release-only collection). Ad revenue flows in as Firebase `ad_impression` events via `AdEvents`; product-funnel events via `analytics/Analytics.kt`. `google-services.json` goes in `app/`. |
| **Ads** | AdMob. Banners + native in library chrome; never on the player surface. **One interstitial placement (changed 2026-11-18, user-approved): leaving the video player after ≥ 60 s of real watching**, gated by `AdFrequencyPolicy` (24 h + 2-session grace, 4 min gap, 3/session, 8/day, 10 min after a rewarded ad, never after an external open, all Remote-Config tunable with kill switches). Never during playback, on launch or in PiP. Pro removes every ad it didn't ask for. |
| **Theming** | One `VixPlayTheme(mode, accent)` (`ui/theme/Theme.kt`) fed by `ThemeViewModel` from DataStore. `ThemeMode { SYSTEM, LIGHT, DARK, AMOLED, DYNAMIC }` — **default `LIGHT`** (changed 2026-11-18); `DYNAMIC` = Material You on API 31+. Optional accent override (`AccentChoice`). Tokens live in `ui/theme/Color.kt`; components read `MaterialTheme.colorScheme` or those tokens. The video player surface (scrims, HUD) stays dark in every theme by design. |
| **Android TV** | Compose for TV (`androidx.tv`), not Leanback. Keeps the entire UI layer in one paradigm. |
| **Private folder recovery** | Recovery code shown at PIN setup (hashed locally). No email recovery — that requires a backend. |

## Design system

Brand: Orbit mark, indigo→violet (`#6D5BFF → #B24BFF`), dark bg `#121316`, AMOLED `#000000`. Fonts (in `res/font/`, defined in `ui/theme/Type.kt`): **Inter** for UI, **JetBrains Mono** for timecodes.

## Key constraints

- **No hardcoded colours.** Every component reads semantic tokens / `colorScheme`. The #1 theming rule — retrofitting is the worst rewrite. Theme-independent exceptions are the over-video scrim tokens and the splash brand gradient.
- **No ads on the player surface.** Banners/native only in library chrome; the single interstitial fires *after* leaving the player (see Ads).
- **AC3/DTS omitted** — do not add software decoders without legal review of the Dolby/DTS license situation.
- **FFmpeg must be LGPL build** — audit build flags before adding any GPL-only components; GPL taints the whole app.
- `minSdk = 24`, `targetSdk = 36`. Material You requires the runtime API 31+ check `VixPlayTheme` already does.
- Resume positions use MMKV (not DataStore) — DataStore's coroutine overhead is too slow for per-seek writes.
- Release signing reads `keystore.properties` (git-ignored); never commit keystores or passwords. Each Play upload needs a higher `versionCode`.

### 2026-11-21 — Series Mode, phase 3b: automatic intro detection — DONE, **verified on a Samsung A55 (Android 16) and offline on real episodes: House of the Dragon S1 found in 9/10 episodes (0:00–1:44; the premiere has no title sequence) — pill + "Found automatically" + skip to 1:44 on device, result reused without rescanning; Peaky Blinders S1 and Paatal Lok S2 correctly find none. 89 unit tests pass (+1 opt-in tuning test). Not exercised on device: "Not the intro".**
- **How:** `player/intro/AudioFingerprinter` (Haitsma–Kalker band-energy fingerprint: mono 5512 Hz, 2048-sample frames, a 32-bit code per 100 ms from 33 log-spaced bands 300–2000 Hz) over the first 10 min (or half) of each episode; `IntroMatcher.shared` tries **every** alignment of two episodes (exact-code voting failed — real encodes of one theme differ in ~9 of 32 bits, so there are no exact matches), scores the best 10 s of "close" frames, takes the 12 best alignments (music repeats, so shifted ones match too) and keeps the longest run whose 2 s-average bit difference is ≤ 10; `introOf` takes the stretch most of up to 4 neighbouring episodes agree on (median start/end). Shared stretches must be **15 s–3 min**.
- **Why 15 s:** Peaky Blinders' title song plays under each episode's own scenes, so episodes share only 10–15 s pieces of it at loose thresholds; Paatal Lok S2 shares only a 5–6 s logo at 0:00. Both now come out "none" and fall back to the manual mark rather than offering a misleading skip.
- **Where it runs — in-process, not WorkManager.** First built as a `@HiltWorker`: on this Samsung a normal job sat READY for minutes, and an expedited one needs quotas plus (below Android 12) a foreground notification; reinstalls also left jobs stuck RUNNING, which `KEEP` then honoured. Now `IntroDetection` (`@Singleton`, own `SupervisorJob` scope) scans a season when one of its episodes opens; a scan interrupted by process death just isn't marked done and restarts on the next open. One scan per show at a time.
- **Speed:** MediaCodec makes a round trip to the system codec process per ~21 ms buffer — **~25 s (AC-3) to ~57 s (AAC) per 10 min**. FFmpeg's decoder in-process does it in **~6 s**, so the scan decodes with it first via `androidx/media3/decoder/ffmpeg/IntroFfmpegAudio.kt` — **in Media3's package because `FfmpegAudioDecoder` is package-private there** (safe: the extension is our pinned `.aar`; a Media3 bump means re-checking this file along with the rebuild). Codecs our FFmpeg build omits (AC-3 — House of the Dragon) fall back to MediaCodec. 4 episodes decode in parallel; **the episode being watched and its 3 nearest go first**, so its result (and a player reload via `episodeReady`) lands after one round; the rest follow. Paatal Lok S2 (8 eps, AAC): 16.6 s total. House of the Dragon S1 (10 eps, AC-3): first result 61 s, season 164 s.
- **Storage:** per file in MMKV `introauto_v2_<id>` = "start,end" / "none" / "rejected" (a rejection is never overwritten by a rescan); per season `introscan_v2_<showKey>|<season>` = the sorted episode ids it was scanned with (a new episode → rescan). Versioned so a better detector can rescan everything.
- **Precedence (`resolveIntro`):** this episode's manual mark > detected > the show's manual mark (detection is found in the very file, so it follows a longer cold open; the show's fixed offsets are the fallback). `IntroSource.DETECTED`: panel says "Found automatically", hint "Found in this episode's audio — set new times to correct it", and the remove button is **"Not the intro"** (→ "rejected" for that file). Tile shows "Finding…" while a scan runs.
- **Tuning tools:** debug builds write each fingerprint to `cache/intro/<showKey>_<code>.bin`; `IntroTuningTest` (skipped unless `INTRO_TUNING_DIR` is set) runs the real matcher on such dumps or on WAVs (`afconvert -f WAVE -d LEI16@5512 -c 1 ep.mp4 e01.wav`) and prints each pair's longest run at several thresholds. Gradle caches the test — use `cleanTestDebugUnitTest` when changing the directory.
- **Not done / honest gaps:** end-credits detection (for Up Next), intros past the first 10 minutes, a progress indicator beyond "Finding…", and battery cost has not been measured (the scan runs once per season, while an episode is open).
- Files: `+player/intro/{AudioFingerprint,IntroMatcher,IntroAudioDecoder,IntroDetection}.kt`, `+androidx/media3/decoder/ffmpeg/IntroFfmpegAudio.kt`, `IntroSkip.kt` (+`DetectedIntro`, `IntroSource.DETECTED`, `resolveIntro(detected)`), `PlaybackRepository.kt` (+detected/scanned storage), `PlayerViewModel.kt` (+`startIntroDetection`, `introDetecting`, `introEpisodeReady`), `PlayerScreen.kt` (trigger + reloads, "Finding…"), `IntroHud.kt` (+source line, detected hint, "Not the intro"), `+IntroMatcherTest` (5), `+IntroTuningTest`, `IntroSkipTest` (+1).

### 2026-07-23 — Move / copy files — DONE, **not yet device-verified. Long-running and file-touching.**
- **Q1=A — copy is the primitive; move is copy-then-delete, source removed only after the copy is published.** One verified data path instead of two optimised ones. Slow, wears storage, and can fail on a nearly-full device. That fast path is deliberately **deferred until the safe path is proven on hardware** — shipping both untested at once is how you end up unable to tell which one broke.
- **Q2=A — modal progress dialog with Cancel, running in `viewModelScope`.** Per-file `LinearProgressIndicator` plus "3 of 7". ### 2026-07-23 — Bulk delete (multi-select) — DONE, **not yet device-verified. Destructive — verify before trusting.**
- **Built against a stated recommendation.** I twice advised doing the device pass *first*, because every other unverified feature fails recoverably (a wrong queue, a blank notification, a janky drag) while this one destroys the user's files. The user reaffirmed, so it was built — with the safety design tightened accordingly. **This is the one feature where an unverified selection bug is not recoverable.**
- **Q1=A — use the platform's confirmation where it exists; supply our own only where it doesn't.** New `MediaDeleter` handles all three Android flows: **API 30+** `MediaStore.createDeleteRequest` → the **OS** shows its own dialog with thumbnails; **API 29** direct delete throws `RecoverableSecurityException` whose `IntentSender` yields the same system prompt; **API 24–28** direct delete under the `WRITE_EXTERNAL_STORAGE` the manifest already caps at `maxSdkVersion="28"` — **no system confirmation exists on that path**, so the app shows an `AlertDialog` naming the count and stating it can't be undone. Rejected B (always our dialog *plus* the system one — two dialogs for one action trains people to dismiss without reading, making confirmation *less* effective) and C (30+ only — `minSdk` is 24, so it would silently do nothing for a slice of users).
- **Safety hole found and closed during implementation.** `systemConfirms()` initially returned `SDK_INT >= Q` (29). But on 29 the system prompt appears **only for files the app doesn't own** — an app-owned file would have been deleted **silently, with no confirmation from anyone**. In practice the audio library holds the user's own music so it would always prompt, but "in practice" is not a safety argument for an irreversible operation. Changed to `>= R` (30). Consequence: on API 29 a non-owned file may show **two** prompts (ours, then the system's). That redundancy is the correct trade — **no path may delete without at least one confirmation**.
- **Q2=A — re-query MediaStore as the source of truth, then reconcile the queue.** After the result returns: reload the library, clear the selection, close any drill, and report what *actually* happened by diffing the track count before and after — not by reporting what was requested. **The user can deselect items inside the system dialog**, so the request is not the outcome. Rejected B (optimistically drop rows — if deletion partially failed the list would claim files are gone while they're still on disk, the worst failure mode a delete feature can have) and C (skip queue reconciliation — deleting the playing track would leave ExoPlayer on a dead URI and surface as a playback error, reading as a crash).
- **`PlayerController.removeFromQueue(uris)`** walks the queue backwards (so removals don't shift indices still to be checked), drops matches, and stops + clears + sets `PlaybackKind.NONE` if the queue empties. Deleting the current track therefore skips onward rather than erroring.
- **Playlists needed no work**: `rowsFor()` already resolves each item against the live library, so entries pointing at deleted files automatically become "Unavailable — file missing" and are excluded from playback — exactly the behaviour the playlists pass built for this case.
- **Outcome reported honestly**: "3 files deleted" / "1 file deleted" / "Nothing was deleted" / "Delete cancelled", from the observed count difference.
- Files: `+data/repository/MediaDeleter.kt` (`DeleteResult`); `PlayerController.kt` (+`removeFromQueue`); `AudioLibraryViewModel.kt` (+`deleteSelection`, `onDeleteConsentResult`, `finishDelete`, one-shot `message`); `AudioLibraryScreen.kt` (delete action, `StartIntentSenderForResult` launcher, API 24–28 confirm dialog, toast).
